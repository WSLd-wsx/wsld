# ADR 010: Preserve the verified Guest RAM reclaim profile

Status: repeated runtime quota failure diagnosed; Core wiring corrected and built;
current product interaction retest is separate from historical prototype evidence.

## Observed failure

On 2026-11-05 the user reproduced the freeze after repeated screensaver entry/exit
and leaving the menu open. The independent Windows trace records the 300th
`HdvCreateGuestMemoryAperture` call returning `0x80070718` at
08:21:51.880671 UTC, elapsed 0 ms, with a null address. There were 299 successful
4 KiB mappings and no aperture-destroy calls. The cache retained 300 slots,
299 usable pages and one uncertain slot. Available physical memory was
53,401,272,320 bytes. HCS exit checks continued to return timeout successfully
through 08:21:53.895331, so this failure preceded confirmed VM loss and was not
introduced by an agent service restart. All traced begin calls have end records.
The runtime then entered its existing failed-stream quarantine. Windows
`Responding=true` did not indicate queue progress.

This establishes the immediate runtime failure, not which undocumented Windows
resource set the quota. Both observed product lifetimes failed at 300 retained
slots, but 299 is not asserted as a universal platform limit. Screensaver/menu
activity exposed cache growth; it is not established as an image or GPU defect.

Evidence: `artifacts/interactive-hang-20261105-01`, including original trace,
Native log, Windows sampler and `trace-analysis.json`. The original failed Host
and VM identities are preserved. Recovery after the user's explicit authorization
is recorded separately in `artifacts/authorized-ram-recovery-20261105-01`.

## Migration defect and correction

The reference already implements safe batch-boundary cache reclamation and has a
real `guest_ram_reclaim_pages=64` profile trial. Core omitted this optional field;
the Host therefore selected its 1024-page default. That watermark was unreachable
before this machine's observed mapping failure, so no cache reclaim occurred.

Core now emits `guest_ram_reclaim_pages=min(64,max_guest_pages)` explicitly.
The low watermark remains the existing Native implementation's half (normally
32). The larger admission budget, GPU resources, fences, device/kernel protocol
and Native binaries are unchanged by this fix. Reclaim still requires exclusive
view ownership at a scoped batch checkpoint. An uncertain map/revoke remains a
terminal retained failure; live slices are never evicted to retry it.

This reuses the reference mechanism and its selected profile. It is not a new
cache implementation, a general cure for every quota, or proof that a single large
batch cannot fail. No Iris/RTX branch is introduced. The concrete migration
cross-check is [PROTOTYPE-MIGRATION-CHECKLIST.md](PROTOTYPE-MIGRATION-CHECKLIST.md).

## Build and acceptance

`artifacts/ram-reclaim-build-20261105-01` passed 46 Windows/MSVC tests. The new
profile test checks serialization, nonzero/budget-clamped watermarks, unchanged
admission and adapter-independent policy. The three identical public PEs have
SHA-256 `c1719ad1c0daf5234f6a34015c27a2735a2660abb8932a5d837902f6dd877380`.
The previously built diagnostic pair is reused unchanged as
`reference-a2485afcee73`; no additional graphics rebuild was necessary.

The pinned reference trial's 17 actual HDV reclaim cycles and 645 presentations
were checked against its log and profile, not just its summary. That trial remains
historical Iris Xe/CachyOS evidence. Current Omarchy/RTX interaction, sustained
growth beyond 300 cumulative mappings and eventual normal retirement must be
recorded independently; build success is not desktop acceptance.

## Initial product retest observation

The user authorized terminating only failed Native PID 22012 after the original
VM was absent. Logs were preserved and forced recovery remains distinct from
normal retirement. Fresh Guest checks found no loaded modules or retained owner;
no module unload, WSL/Windows restart or service change was performed by the agent.

The fixed CLI started Native PID 16972 / instance
`2fbd2e79-b52d-46bc-bb61-004d39b61b55` in VM
`3743ba19-1f48-4da9-83eb-dfecee743649`, with actual profile high watermark 64.
At 08:34:21 UTC, archived trace showed 1,644 successful aperture creates, 1,589
successful destroys, 50 completed cache reclaims (all to 32 usable pages), and
2,407 presentations, including 15 after the last reclaim. No HDV map/unmap error
or failed-stream quarantine was present. These are current Omarchy/RTX observations,
separate from the prototype evidence. Native log/stderr snapshots are sequential,
not an atomic counter capture. User screen/menu repetition acceptance is pending;
normal retirement was not rerun. Evidence is
`artifacts/ram-reclaim-start-20261105-01/ram-observation.json`.

The user subsequently confirmed that repeating screensaver entry/exit and menu
interaction remained normal. This passes that bounded reported interaction case,
with real reclamation and continued frames independently observed. It does not
claim indefinite stability, all applications, or normal retirement of this lifetime.
The desktop is left running. The confirmation is archived in `user-acceptance.json`.
