# ADR 008: Post-shutdown interactive stall remains unresolved

Status: real restart initially worked, then became unresponsive; diagnosis in progress.

Diagnosis update: [ADR 010](ADR-010.md) records the diagnostic retest's quota
failure before VM loss and a concrete migration omission: Core failed to select
the reference's verified 64/32-page CPU-cache profile. That wiring is corrected;
new interaction acceptance remains separate. Earlier unknown-order statements
below describe the first lifetime, whose logs still lack call timestamps.

Follow-up: [ADR 009](ADR-009.md) records the user-authorized termination of the
retained Host and current-authority startup policy. The diagnostic pair below is
now admitted by that new Core for explicit selection; it remains a diagnostic
change, not a hang fix. Earlier undeployed statements describe the build cutoff.

The successful bounded shutdown in ADR 007 does not establish interactive stability
of the next desktop. On 2026-11-05 the compiled public CLI returned 0, recorded a
new first frame, and a live query observed the exact Guest session active/running.
The user confirms initial interaction and manually starting the screensaver.
Later, the renderer and WSL-hosted command execution became unresponsive. The user
reports two such occurrences and recovered by stopping WSLService and restarting
WSL. The agent did not perform that service recovery. The exact point at which
the screensaver stopped animating is unknown; the green screenshot is not evidence
of graphics corruption or a known screensaver-specific trigger.

- Failure readback: `artifacts/post-shutdown-hang-20261105-01`.
- Native PID 14364, creation FILETIME `134383376443370747`, instance

  `3a3cede7-5de1-4747-b85b-777013b56dc0`.
- Startup used default cache `reference-565b64806b7f`, without module removal or
  reload. All nine registration identities were unchanged at the live query.
- The final Native log contains 9,292 presentation records, then a Guest RAM map
  failure at GPA `0x103fde000`: HRESULT `0x80070718`, null returned aperture,
  300 retained slots / 299 usable pages. The Host entered its retained-failure
  path and remained present after the user's service recovery.
- `native.stderr` records 54,266,191,872 available physical bytes at the error.
  The underlying Win32 code is 1816, `ERROR_NOT_ENOUGH_QUOTA`
  ([Microsoft error reference](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--1700-3999-)).
  This does not identify which quota, prove a leak, or imply physical RAM exhaustion.
- Original per-call timing is absent. The mapping error may be a cause, or a later
  consequence of service/VM loss. Do not infer ordering from the final log write
  time or the location of the final error alone.
- A later Windows process observation reported `Responding=true` for the retained
  failed Host. That property is not proof of queue progress or desktop health.

Do not restart a desktop while this retained Owner is present. Do not kill it,
unload modules, recycle descriptors or stop services to make acceptance pass.
Its absence after some later recovery would not prove normal retirement.

## Diagnostic changes

The graphics integration now supports opt-in `WSX_TRACE_NATIVE_CALLS=1`. It writes
flushed begin/end records for Guest aperture creation/destruction and the original
HCS VM-exit query, with PID/TID, API, sequence, UTC FILETIME, monotonic elapsed time,
HRESULT and GPA where relevant. Sequence values are local to a C translation unit;
correlate them with PID, TID and API. No password, account credential or application
payload is logged. Diagnostics preserve LastError and do not change return values,
ownership, calling thread, timeout policy or reclamation decisions. A missing end
record is a diagnostic lead, not authority to cancel or release the call.

`scripts/observe-native-runtime.ps1` is a finite read-only test tool, not a product
service. Copy it to a new local Windows diagnostics directory and run it from an
independent Windows PowerShell terminal. Both its receipt and output paths must be
local Windows paths. It verifies the original process creation identity and samples
process/thread observations and bounded 64 KiB log suffixes with timestamps. It
does not execute WSL/HCS discovery, so it cannot itself prove VM or Guest health.
It never restarts, stops, kills, signals retirement or retries a hung Guest command.

```powershell
# For a future, explicitly prepared diagnostic build and test lifetime:
$env:WSX_TRACE_NATIVE_CALLS = '1'
# Start the admitted diagnostic lifetime through wsld, then in Windows PowerShell:
.\observe-native-runtime.ps1 -Receipt C:\path\to\owned-lifetime\native.json -Evidence C:\path\to\new-evidence -Seconds 600
```

The diagnostic pair must be separately hash-verified and admitted before a live
test. Merely setting the variable cannot instrument an already running old Host.
It may increase log volume and alter timing; a no-trace comparison remains useful.
The next live test needs the Windows-local collector active before interaction,
separate observation of input/frame/Guest progress, and evidence preserved before
any user-directed service recovery. No additional shutdown or hang reproduction
was executed while collecting this readback. Resolution/DPI work is deferred until
the stability regression is understood.
