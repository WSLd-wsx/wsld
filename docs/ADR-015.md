# ADR 015: Per-desktop graphics paths

> Historical experiment paths referenced below were moved to the prototype repository; see [Experiment migration](EXPERIMENT-MIGRATION.md).

Status: historical design record. Product integration and current acceptance are recorded in ADR-016; statements below describe the earlier implementation state.

The product will use opaque-v1 zero-copy as its preferred graphics path and
staging-copy as its automatic fallback. Both paths use the Linaro-derived
virtio-msg Host peer. Select one independently paired Host and renderer per
Owner lifetime; share verified source modules where practical. In normal
operation different paths do not run concurrently on the same machine.
This decision adopts the experimental direction; it does not promote a test
bundle, accept a license on the user's behalf, or claim a finished release.

The normal Windows build embeds the independently compiled opaque probe and
connects the selection policy to the machine admission gate. It verifies the pinned opaque reference and Guest
preflight, tests a matching-adapter opaque buffer import and queries
representative LINEAR image capabilities. On RTX 3080 Ti the r12 acceptance
build selected zero-copy, presented a desktop, and retired normally. The image
query does not prove every image allocation will succeed. Unknown or failed
observations do not establish that staging is supported. Staging remains
diagnostic-only and is not an automatic fallback yet.

The `simulated-fallback` acceptance feature deliberately supplies an
unsupported opaque result to the same selection policy after diagnostic
component and temporary Guest shadow checks. It writes an explicit simulation
record and cannot admit a product runtime. On Iris Xe with Omarchy r14 this
selected and started the staging Host, and the user confirmed display and input.
Automatic display fitting failed with a Guest JSON parse error; the command
returned failure and the lifetime remained recorded as failed. The user then
authorized normal stop; Guest/PCI retirement, zero retained slots and Host exit
were observed. This is not evidence of real opaque capability failure, an
admitted staging component closure, or a released Guest image.

Each desktop already has one Native Host process and one retained renderer.
Choose a single verified path before creating that desktop's graphics owner.
The currently shipped opaque-v1 Host and renderer remain the existing baseline
until the Linaro-backed pair is integrated. The staging Host and renderer must
be a separately built and admitted pair. They
must own the same desktop's device and resource lifecycle; they are not an
additional business service or a frame-transfer sidecar. In normal product
operation all active Owners on a machine must use the same path. A different
path is permitted only after existing Owners are safely retired. Explicitly
authorized diagnostic tests may exercise mixed paths; this is not a product
default or an automatic recovery mechanism.
Current startup verifies live peers against the existing pinned opaque-v1
receipts while holding the machine admission gate. An unknown or diagnostic
peer is rejected; no staging peer is product-admitted yet. The negotiated
Guest path is checked against that observation before Owner creation. This
check is not Vulkan capability selection, nor does a Guest preflight prove
hardware support.
The eventual launcher must serialize discovery and Owner creation across
processes, recheck live Owner identities while holding that gate, and fail
closed if the active path cannot be established. The selection helper alone
does not provide this atomicity or a process-wide persistent state record.
Derive the staging pair from the verified zero-copy Host, renderer and device
retirement baseline. Port only the necessary staging transfer changes and
their validated dependencies. The historical standalone prototype Owner is
not a replacement for that baseline and is not a product dependency.
Prefer compiling the same source for shared behavior in both processes, with
staging-specific code selected at build time. Avoid independently maintained
copies. Reuse does not permit adding staging work or runtime branches to the
existing zero-copy hot path without separate verification.

No renderer switching is permitted within an active Owner. A retry on another
path requires confirmed safe retirement of the previous Owner. An uncertain
GPU result or failed retirement retains the previous lifetime; it is not a
reason to start another owner against the same resources. Capability failures
must not hide configuration, integrity, or device-lifetime failures.

Separate processes isolate per-desktop state but not the shared GPU driver,
WSL VM, kernel, device, or threads inside a renderer. In particular the Venus
ring has its own execution thread. A staging implementation still needs proven
resource identity and retention, queue synchronization, actual GPU completion,
data visibility, and Guest/renderer/device retirement. Process exit alone is
not proof of safe GPU or device retirement.

Reuse the baseline's Session retirement entry points, resource-specific queue
fence polling and queue error latch. The existing resource fence is submitted
after Guest reference admission closes and is polled with `vkGetFenceStatus`;
pending or error is not retirement. Staging must additionally prove that its
own transfer, readback and publication are complete before those baseline
barriers can authorize release. The prototype's private fence is not currently
registered with that baseline and an uncertain transfer remains retained.

The separate `integration/graphics-staging/build-candidate.py` entry builds a
candidate from explicitly supplied pinned reference material. Its default is
compile-only with staging disabled; an explicit diagnostic build enables the
candidate renderer for isolated tests. Neither form emits an admissible runtime
bundle. The candidate ports Section tracking into the existing Session; the
superseded independent Owner and mailbox experiments are not selected.

The candidate Host checks the renderer's staging mode before COM or device
construction and rejects a mismatch. On Windows,
`artifacts/staging-pair-mode-matched-20261108-01/` and
`artifacts/staging-pair-mode-mismatch-20261108-01/` exercise the matching and
deliberately mismatched cases without creating a device. Candidate build
validation checks the actual sizes and hashes of the four recorded Windows
outputs, including the pinned libepoxy dependency used by the renderer.
The mode check and these local receipts do not authenticate a publisher, prove
an ABI match, supply a Guest/kernel deployment closure, or authorize product
admission.

`artifacts/staging-closure-20261108-01/` is the first candidate build that
includes its own verified `libepoxy-0.dll`. Its four PE files are x86-64. The
isolated Host entry check in `artifacts/staging-closure-entry-20261108-01/`
uses only the candidate's two graphics DLLs and rejects the intentionally
missing launch arguments before device construction. The independent Iris Xe
window fixture in `artifacts/staging-closure-gpu-20261108-01/` exercises the
same renderer and libepoxy; it does not run a Guest or validate HDV mappings.

Staging admission requires an independently versioned and hash-verified paired
component closure, source and license provenance, explicit capability checks,
bounded failure behavior, and real desktop/retirement acceptance on supported
GPUs. A test of an empty Vulkan queue or a compile-only candidate is not that
acceptance. No automatic transition from opaque-v1 has yet been implemented.
