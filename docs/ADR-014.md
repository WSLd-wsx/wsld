# ADR 014: Staging identity and asynchronous ownership

Status: superseded as a prescribed architecture by ADR-015. This record and
its fixtures remain historical evidence; staging is not admitted.

## Existing constraints

The Native Host mapping Session exclusively owns the production Rutabaga
instance, mapping leases and retirement gates. The renderer's Venus command
execution can be entered from a synchronous `submit_command`; queue submission
also holds the Windows scanout and queue synchronization locks. A renderer
callback cannot safely reenter that Session or wait for its owner thread while
that thread waits for the callback. A mutex or lock-free queue alone does not
break that cycle.

The historical `wsxr_owner` constructs a separate Rutabaga and resource
table. Its ABI 3 adapter is reference material only, not an implementation of
the production Session API. Similarly, a renderer virtual address or Vulkan
handle by itself does not establish a Session resource identity.

## Identity

The Session is the only registration authority. On a successful, provenance-
checked mapping and renderer association it issues an identity containing
Session epoch, context, resource ID and non-repeating mapping generation.
Registration checks actual mapping extent, access mode, association and
allocation provenance; numerical address equality is not proof. Ranges must
not overflow or ambiguously overlap. The address index is metadata used only
to resolve a live registered interval. Transfer messages contain the identity,
offset and length, never an address to dereference. The Session resolves and
checks these against its existing Rutabaga resource and retained mapping.

Detach, unmap and unref first close admission for the exact generation.
Registration stays pinned through all outstanding slots and native fence
rundown; it can be removed only after the existing Session retirement proves
that exact mapping and all callback users have ended. A stale identity cannot
refer to a replacement mapping or another distro's Session.

## Mailbox and scheduling

Use a bounded per-Session in-process queue with owned payloads and generation-
checked slot handles. It is neither a service nor an IPC replacement for Core.
Capacity and byte budgets are checked before resource borrowing; queue-full
returns a retryable error before side effects. Slots cannot carry borrowed
pointers or mutable Session references. The initial supported profile must
explicitly restrict queue topology, Vulkan extensions and host-visible memory
to the subset actually verified by the prototype; unsupported combinations
fail before submission.

Execution must be split into continuations so the Session owner can consume
requests while no mutable Rutabaga borrow is outstanding. In particular:

1. At an owner-thread safe point, resolve identities, retain original resource
   leases, reserve bounded slot storage and capture upload bytes. No renderer
   callback may synchronously request a second mutable Session borrow.
2. The renderer receives only the slot handle and owned upload payload, copies
   into its retained Vulkan mapping, flushes it, and submits GPU work with a
   retained native completion fence. Vulkan queue external synchronization and
   the existing scanout lock contract remain in force.
3. After an actual fence signal, the renderer invalidates and copies readback
   into owned slot storage. The Session owner validates the same identity and
   publishes the readback through the original resource authority.
4. Application fences and semaphore signals are made visible only after
   successful publication, respecting original queue order. The Session
   releases the slot and resource borrow only when publication, native fence
   and all callbacks have actually completed.

This ordering requires a cooperative submit/decoder continuation on the
existing owning thread. Merely placing requests on a queue while the owner remains
blocked inside `submit_command` deadlocks. The current renderer and Session
do not yet implement this scheduling or a safe point; no runtime should
advertise this design as a capability.

The Native Host HDV mapping owner is bound to its initialization thread and
the pinned Rutabaga library is not thread-safe. The separate decoder-worker
experiment is superseded; it is not a product direction. The cooperative port
must retain the original thread ownership. Decoder continuation must cover the
context, ring and transport dispatch paths: a single dispatched Vulkan command
may still block, so a command-count budget alone is not a time bound.

Each Native Owner chooses one admitted rendering path for its lifetime, either
direct sharing or staging. The choice is not repeated for each frame or each
resource. One owner still has multiple resources and submissions; their
identities, mappings and actual GPU completion must remain independently valid
until safe retirement.

## Failure and retirement

The transaction tracks prepare, submitted, fence pending, readback ready,
published and retired states. Slot IDs and fence ownership are generation-
checked. Unknown GPU results, timeout, device loss, publication ambiguity,
callback failure and lost owner retain the original slot, mappings, fence and
Session authority. No later command invents completion or replays an uncertain
GPU operation. Normal unmap, detach, unref, context drain and shutdown consult
the existing Session borrow gate. A future recovery path requires independent
evidence of the exact GPU, renderer, Guest and callback rundown.

## Verification

First test stale identity, overlap, bounds, revocation, backpressure, concurrent
contexts, reentry and failure at every phase without a GPU. Next exercise the
actual paired Host and renderer with Vulkan validation, real fences, controlled
timeouts and retirement; compare the unchanged direct path. Only then run owned
desktop and multi-distro acceptance. Independent Vulkan transfer probes and
compilation are not product desktop or retirement acceptance.
