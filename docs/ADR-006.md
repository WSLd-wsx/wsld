# ADR 006: Reconcile exited-VM apertures and pre-bind both retirement helpers

> Historical experiment paths referenced below were moved to the prototype repository; see [Experiment migration](EXPERIMENT-MIGRATION.md).

Follow-up: [ADR 007](ADR-007.md) adds fresh VM/Host recovery without requiring a Windows restart.

Status: implemented; isolated Windows API and regression tests passed. Real
Omarchy whole-WSL shutdown subsequently passed with the ADR 007 Core build; the
invalid-handle fallback was not triggered in that desktop run.

## Observed failure

The real shutdown in ADR 005 confirmed the original HCS VM exit but failed at
Guest RAM lease close with `0x80070006`. Native PID 18984 remained quarantined.
A normal-close `wsl --exec` retirement command could also race shutdown and
attempt to enter a stopped distro. Neither missing VM nor a failed unmap is a
complete native/GPU retirement proof.

## Aperture decision

Retain the original HCS handle borrowed from the direct bootstrap in the opaque
native Host; the bootstrap already outlives native Host closure. On an exact
`ERROR_INVALID_HANDLE` result from `HdvDestroyGuestMemoryAperture`, require both:

- Successful `HcsWaitForComputeSystemExit` on that retained original handle.
- `VirtualQuery` reporting `MEM_FREE` across the entire original CPU aperture.

Only then clear the aperture lease and release its device reference. Ordinary
successful unmap is unchanged. Pending/error VM observations, invalid or unknown
ranges, partial release, reserved/committed/reused ranges and query failures retain
the original mapping identity and error. Do not guess with `VirtualFree`, reopen a
VM by name, or reinterpret every invalid handle as success. Rust exclusive-view
checks, GPU/context/completion drains, Section backing retirement, successful HDV
teardown, callback rundown and final process exit remain mandatory independent
barriers. No Core retirement-evidence checks are weakened.

This policy is supported by an isolated real Windows test, not just the error
number: a newly created diskless 256 MB HCS VM with its own HDV test device mapped
RAM successfully. After terminating only that owned VM, its aperture was already
`MEM_FREE`; HDV destroy returned `0x80070006`; the production reconciliation policy
returned success and HDV teardown returned `S_OK`. The same test rejected a live
VM and successfully unmapped another aperture normally. No WSL shutdown or GPU
rendering was involved. A future OS behavior that retains/reuses the virtual range
will refuse this recovery path instead of assuming identical cleanup semantics.

[HCS lifecycle](https://learn.microsoft.com/en-us/virtualization/api/hcs/overview)
describes exited compute systems and the retained exit query.
[VirtualQuery](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualquery)
reports CPU virtual-address ranges; it is not a GPU retirement guarantee.
[HDV teardown](https://learn.microsoft.com/en-us/virtualization/api/hcs/reference/hdv/hdvteardowndevicehost)
remains a separate required native operation.

## Retirement command decision

Create two private stdin-controlled helpers before desktop readiness, and require
both handshakes while observing the original VM:

- Guest helper: the verified existing Python retirement implementation, including
  exact-instance PAM session and systemd unit shutdown, then synchronous PCI retire.
- System helper: existing exact-instance kernel retirement for a distro that has
  already stopped.

Normal close signals the pre-bound Guest helper. Observed external distro stop
signals the pre-bound system helper. If the first helper is interrupted by distro
termination, fallback consumes the already existing system helper. Confirmed VM
exit can discharge Guest admission; helper failure alone cannot. A bounded HCS
reconciliation window handles helper exit preceding VM-exit notification. Closing
never launches a new `wsl --exec`, and no replacement helper is spawned. Unused
helpers receive EOF and exit; final success observes all helpers naturally exit.
Read-only WSL running-list queries remain bounded. No daemon, service or persistent
business state is added.
